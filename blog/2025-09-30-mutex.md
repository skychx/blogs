## 初步实现

### 最小案例

我们先假设一个最简单的并发场景，有一个用于用户注册的类 UserRegistry，每次可以调用 register 注册一个新用户：

```typescript
const delay = (num: number) => new Promise((resolve) => setTimeout(resolve, num));

class UserRegistry {
  private users = new Set<string>();

  public async register(username: string): Promise<boolean> {
    if (this.users.has(username)) {
      return false;
    }

    await delay(Math.random() * 100); // 模拟其他的异步操作耗时
    this.users.add(username);

    return true;
  }
}
```

这个 register 函数实现上读写分离，而且有不确定的异步耗时，如果外界几乎同时注册一个名为 'Bob' 的用户，就会出现多个用户都注册成功，但是实际只有一个 user 注册的多对一情况：

```typescript
const center = new UserRegistry();

Promise.all([
  center.register('Bob'),
  center.register('Bob'),
  center.register('Bob'),
]).then((results) => {
  console.log(results); // 期望：[true, false, false]，实际：[true, true, true]
});
```

这种典型的竞态问题，核心就是 `register` 方法里的检查和插入不是原子的：中间隔了一个 `await`，三次调用会先后做完检查（这时候 Bob 还不存在），然后才陆续插入，检查和插入**交错进行**从而引发了 BUG。

### 队列化处理

遇到这种问题的时候，其实一个自然而然的思路就是队列化处理。每次执行 register 的时候，并不会直接执行内部的 task，而是把这个 task 推到一个队列里去，然后依次执行这个队列里的代码。

这个改造也比较简单，先创建一个队列，每次执行 register 时，把真正的逻辑包装成一个 task 接到队列的尾部，等前面的 task 都执行完了再执行它。在 JavaScript 里，这个队列直接用一条 Promise 链就能表示：

```typescript
class UserRegistry {
  private users = new Set<string>();
  private queue: Promise<unknown> = Promise.resolve(); // 队列的尾部

  public register(username: string): Promise<boolean> {
    const task = this.queue.then(async () => {
      if (this.users.has(username)) {
        return false;
      }

      await delay(Math.random() * 100);
      this.users.add(username);

      return true;
    });

    // 不管 task 成功还是失败，队列都要继续往下走
    this.queue = task.catch(() => {});

    return task;
  }
}
```

再跑一下上面的测试，结果就稳定是 `[true, false, false]` 了。

不过这个写法也有明显的问题：

- 排队的逻辑和业务逻辑耦合在一起，每个需要互斥的方法都要这样包一层，很难复用
- 整个方法体都在队列里执行，没法只锁住其中一小段代码。比如参数校验、和 Bob 无关的网络请求，其实都不需要排队

所以更好的做法是把「排队」这个能力单独抽出来，做成一个互斥锁（Mutex）：调用 `acquire()` 拿锁，拿不到就等着；用完之后调用 `release()`，把锁交给下一个人。

## 使用 Promise.withResolvers

实现 Mutex 的关键在于「等」：锁被占用时，`acquire()` 要返回一个暂时不会 resolve 的 Promise，等上一个持有者调用 `release()` 的时候，再从外部把它 resolve 掉。

以前想在 Promise 外部拿到 resolve，只能这么写：

```typescript
let resolve!: () => void;
const promise = new Promise<void>((r) => {
  resolve = r;
});
```

这种写法太常见了，很多库都会封装一个 Deferred 类，puppeteer 里也有一个，源码里还留着一句 `// TODO: Switch to Promise.withResolvers with Node 22`。

ES2024 新增的 `Promise.withResolvers()` 就是干这个的，它会把 promise 和对应的 resolve、reject 一起返回：

```typescript
const { promise, resolve, reject } = Promise.withResolvers<void>();
```

有了它，Mutex 写起来就很直观了：

```typescript
class Mutex {
  #locked = false;
  #waiters: Array<() => void> = [];

  async acquire(): Promise<void> {
    if (!this.#locked) {
      this.#locked = true;
      return;
    }

    const { promise, resolve } = Promise.withResolvers<void>();
    this.#waiters.push(resolve);
    await promise;
  }

  release(): void {
    const next = this.#waiters.shift();
    if (!next) {
      this.#locked = false;
      return;
    }
    // 有人在等：锁不释放，直接交给下一个人
    next();
  }
}
```

这里有两个细节：

- `#waiters` 是一个先进先出的队列，先来的先拿到锁，不会有人一直排不上
- 有人在等的时候，`release()` 不会把 `#locked` 改回 `false`，而是直接把锁「交接」给下一个人。如果先置成 `false` 再唤醒，被唤醒的人真正开始执行之前，新来的调用者看到锁是空闲的，也能直接拿到锁，两个人就同时进入了临界区

用起来就是经典的加锁、解锁，`release()` 一定要放在 `finally` 里，不然中间抛了异常，锁就再也释放不掉了：

```typescript
class UserRegistry {
  private users = new Set<string>();
  private mutex = new Mutex();

  public async register(username: string): Promise<boolean> {
    await this.mutex.acquire();
    try {
      if (this.users.has(username)) {
        return false;
      }

      await delay(Math.random() * 100);
      this.users.add(username);

      return true;
    } finally {
      this.mutex.release();
    }
  }
}
```

## 使用 using

到这里 Mutex 已经能用了，但 try/finally 写起来还是有点啰嗦，一不小心就会忘记 release。puppeteer 在这里用了另一个新语法：`using`。

`using` 来自 TC39 的 Explicit Resource Management（显式资源管理）提案，TypeScript 5.2 开始支持。用 `using` 声明的变量，在离开所在的作用域时，不管是正常执行完、提前 return 还是抛了异常，都会自动调用它的 `[Symbol.dispose]()` 方法，有点像 Go 的 `defer` 和 Java 的 try-with-resources。

所以只要让 `acquire()` 返回一个带 `[Symbol.dispose]()` 方法的对象，在 dispose 的时候释放锁就行了：

```typescript
class Mutex {
  #locked = false;
  #waiters: Array<() => void> = [];

  async acquire(): Promise<Disposable> {
    if (this.#locked) {
      const { promise, resolve } = Promise.withResolvers<void>();
      this.#waiters.push(resolve);
      await promise;
    } else {
      this.#locked = true;
    }

    return { [Symbol.dispose]: () => this.release() };
  }

  release(): void {
    const next = this.#waiters.shift();
    if (!next) {
      this.#locked = false;
      return;
    }
    next();
  }
}
```

调用的地方就只剩一行：

```typescript
class UserRegistry {
  private users = new Set<string>();
  private mutex = new Mutex();

  public async register(username: string): Promise<boolean> {
    using _ = await this.mutex.acquire();

    if (this.users.has(username)) {
      return false;
    }

    await delay(Math.random() * 100);
    this.users.add(username);

    return true;
  }
}
```

`using _ = await this.mutex.acquire()` 这一行做了两件事：先 `await` 拿到锁，再用 `using` 把释放锁的动作绑定到当前作用域。之后不管从哪个分支 return，还是中途抛了异常，函数结束的时候锁都会被释放。

这里用的是 `using` 而不是 `await using`：释放锁是个同步操作，实现 `Symbol.dispose` 就够了。如果清理资源本身是异步的（比如关闭文件、断开连接），就要实现 `Symbol.asyncDispose`，再配合 `await using` 使用。

puppeteer 里的实现（[Mutex.ts](https://github.com/puppeteer/puppeteer/blob/main/packages/puppeteer-core/src/util/Mutex.ts)）和上面基本一样：

```typescript
class MutexGuard {
  #mutex: Mutex;
  #onRelease?: () => void;
  constructor(mutex: Mutex, onRelease?: () => void) {
    this.#mutex = mutex;
    this.#onRelease = onRelease;
  }
  [disposeSymbol](): void {
    this.#onRelease?.();
    return this.#mutex.release();
  }
}

export class Mutex {
  static Guard = MutexGuard;

  #locked = false;
  #acquirers: Array<() => void> = [];

  // This is FIFO.
  async acquire(
    onRelease?: () => void,
  ): Promise<InstanceType<typeof Mutex.Guard>> {
    if (!this.#locked) {
      this.#locked = true;
      return new Mutex.Guard(this, onRelease);
    }
    const deferred = Deferred.create<void>();
    this.#acquirers.push(deferred.resolve.bind(deferred));
    await deferred.valueOrThrow();
    return new Mutex.Guard(this, onRelease);
  }

  release(): void {
    const resolve = this.#acquirers.shift();
    if (!resolve) {
      this.#locked = false;
      return;
    }
    resolve();
  }
}
```

区别主要有两点：

- 等待用的是 puppeteer 自己封装的 Deferred，也就是前面说的 `Promise.withResolvers` 的「前身」
- `acquire()` 返回的是一个 MutexGuard 对象，还可以传一个 `onRelease` 回调，在释放锁的时候顺便做些收尾工作。比如 `BrowserContext` 用它来串行化截图操作，同时统计还有多少个截图在排队

在 puppeteer 里，一个典型的用法是 `ExecutionContext` 往页面里注册 binding。多个 `waitFor*` 调用可能同时触发注册，需要等前一个注册完成再执行后面的：

```typescript
// If multiple waitFor are set up asynchronously, we need to wait for the
// first one to set up the binding in the page before running the others.
#mutex = new Mutex();
async #addBinding(binding: Binding): Promise<void> {
  if (this.#bindings.has(binding.name)) {
    return;
  }

  using _ = await this.#mutex.acquire();
  try {
    await this.#client.send('Runtime.addBinding', /* ... */);
    await this.evaluate(addPageBinding, 'internal', binding.name, CDP_BINDING_PREFIX);
    this.#bindings.set(binding.name, binding);
  } catch (error) {
    // ...
  }
}
```

### 兼容性

这两个 API 都比较新，用之前要看一下运行环境：

- `Promise.withResolvers`：ES2024，Chrome 119、Firefox 121、Safari 17.4、Node.js 22 开始支持
- `using`：Chrome 134、Firefox 141、Node.js 24 开始支持，Safari 目前还只在预览版里

TypeScript 里要把 `lib` 设成包含 `es2024` 和 `esnext.disposable`（或者直接用 `esnext`）。如果编译目标不支持 `using`，TypeScript 会把它转成 try/finally，但运行时仍然需要 `Symbol.dispose`，可以像 puppeteer 一样先补一个 polyfill：

```typescript
(Symbol as any).dispose ??= Symbol('dispose');
(Symbol as any).asyncDispose ??= Symbol('asyncDispose');
```

## 和其他语言对比

最后再对比一下其他语言里的互斥锁。还是拿最简单的一个案例说明：假设有个 Inc() 函数要对某个变量做操作，然后用随机 sleep 模拟这个操作的耗时。在 Go 语言里就是类似的伪代码：

```go
type Counter struct {
    mutex sync.Mutex
    value int
}
func (c *Counter) Inc() {
    c.mutex.Lock()
    defer c.mutex.Unlock()

    time.Sleep(time.Duration(rand.Intn(100)) * time.Millisecond)
    c.value++
}
```

可以看到在 Go 语言里主要的用法就是先实例化一个 Mutex，然后在 Inc() 执行前加锁，在 Inc() 执行完毕后释放锁。

Go 语法可能比较甜，我们再换个语言，比如说 Java，可以看到更多的调用细节：先在 Inc() 执行开始时加锁，等具体的逻辑执行完毕后，再在 finally 阶段释放锁：

```java
public class Counter {
  private final ReentrantLock mutex = new ReentrantLock();
  private int value = 0;

  public void Inc() {
    mutex.lock();
    try {
      Thread.sleep(new Random().nextInt(100));
      value++;
    } catch (InterruptedException e) {
      e.printStackTrace();
    } finally {
      mutex.unlock();
    }
  }
}
```

Java 的写法，对应的就是我们前面 try/finally 的版本；而用上 `using` 之后，JavaScript 的写法就和 Go 的 `defer` 几乎一模一样了：

```typescript
class Counter {
  private mutex = new Mutex();
  private value = 0;

  public async Inc() {
    using _ = await this.mutex.acquire();

    const value = this.value;
    await delay(Math.random() * 100);
    this.value = value + 1;
  }
}
```

不过要注意，Go 和 Java 的锁是给多线程用的，防的是多个线程同时读写同一块内存。JavaScript 是单线程的，单独一句 `this.value++` 不会被打断，只有像上面这样读和写被 `await` 隔开的时候，才需要用互斥锁来保护。

## 总结

最后简单总结一下：

- JavaScript 虽然是单线程的，但只要读和写之间隔了一个 `await`，就可能出现竞态问题
- `Promise.withResolvers` 让「在 Promise 外部 resolve」变得很简单，用它可以很方便地实现一个先进先出的等待队列
- `using` 会在离开作用域时自动调用 `Symbol.dispose`，把释放锁绑定到作用域上，再也不用担心忘记 release

puppeteer 的这个 Mutex 只有几十行，但把这几个新语法用得恰到好处，很值得学习。
