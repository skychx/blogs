这篇文章是我「即刻」上一段记录的扩写，个人感觉还是很有意思的。


http 优先级的发展历程很有意思。

### HTTP/1.1

http/1.1，一个 tcp 上按顺序一个一个跑 http 请求就行，不存在优先级的概念。


### HTTP/2

http/2，计划一个 tcp 上可以并发跑多个 http 请求，既然跑多个，就会有权重的概念。

比如说一起跑 abc 3 个请求，如果权重都一样，大家直接排排坐吃果果就好；如果 c 请求比较重要，它的权重就高一些，相同的时间段内，c 的 frame 就多发一些，这样客户端就能早一些拿到 c 的内容。

http/2 为了“完美”的解决这个优先级问题，搞了个非常复杂的策略，每个资源间组成一颗优先级树，从根到叶一层一层过，同层之间还有权重概念，这个权重有多少层呢？256 个。这两个策略乘起来，实际优先级复杂的一批。

毫无疑问，http/2 的优先级策略就是过度设计了。现在推广了这么久，浏览器也就用了很小一部分的调度策略，而服务端很多服务器框架也没有很好的支持优先级策略，丐版又不是不能用，能跑，跑的效果还不错。

### HTTP/3

http/2 已经落入规范并实施多年了，不好改也改不动了，所以 http/3 对优先级策略进行了重新的设计，一共就 8 个优先级，再加一个是否流式传输的开关，比 http/2 简化了太多。

那 http/3 的调度策略可以完美的均衡设计复杂度和现实复杂度吗？其实大家心里也没谱，毕竟当年 http/2 优先级出来时一堆人还吹可以完美解决问题呢。反正 2022 年方案刚刚 release，是骡子是马，先跑几年再说。
