## Initial Implementation

### Minimal Example

Let's first assume a simple concurrency scenario with a UserRegistry class for user registration, where you can call register to register a new user each time:

```typescript
const delay = (num: number) => new Promise((resolve) => setTimeout(resolve, num));

class UserRegistry {
  private users = new Set<string>();

  public async register(username: string): Promise<boolean> {
    if (this.users.has(username)) {
      return false;
    }

    await delay(Math.random() * 100); // Simulate other async operation costs
    this.users.add(username);

    return true;
  }
}
```

This register function implementation has read-write separation and uncertain async delays. If the outside world almost simultaneously registers a user named 'Bob', multiple users might register successfully, but actually only one user gets registered - a many-to-one situation:

```typescript
const center = new UserRegistry();

Promise.all([
  center.register('Bob'),
  center.register('Bob'),
  center.register('Bob'),
]).then((results) => {
  console.log(results); // Expected: [true, false, false], but might be [true, true, true] or others
});
```

This typical race condition problem stems from the fact that the check and insert operations in the `register` method are not atomic, combined with different delay times, causing the check and insert operations to interleave and trigger the BUG.

## Mutex in Other Languages

Let's use the simplest example to explain. Suppose there's an Inc() function that operates on a variable, and we use random sleep to simulate the operation's time cost. In Go language, the similar pseudocode would be:

```go
type Counter struct {
    mutex sync.Mutex
    value int
}
func (c *Counter) Inc() {
    c.mutex.Lock()
    defer c.mutex.Unlock()

    time.Sleep(time.Duration(rand.Intn(100)) * time.Millisecond)
    c.value++
}
```

As you can see, in Go language, the main usage is to first instantiate a Mutex, then lock before Inc() execution, and unlock after Inc() execution completes.

Go syntax might be too sweet, so let's switch to another language, say Java, to see more calling details: lock at the beginning of Inc() execution, then unlock in the finally stage after the specific logic completes:

```java
public class Counter {
  private final ReentrantLock mutex = new ReentrantLock();
  private int value = 0;

  public void Inc() {
    mutex.lock();
    try {
      Thread.sleep(new Random().nextInt(100));
      value++;
    } catch (InterruptedException e) {
      e.printStackTrace();
    } finally {
      mutex.unlock();
    }
  }
}
```

So, following the pattern, if we directly move Java language code to JavaScript, we could write it like this:

```javascript
class Counter {
  private mutex = new Mutex();
  private value = 0;

  public async Inc() {
    mutex.lock();
    try {
      await sleep(Math.random() * 100);
      value++;
    } catch (e) {
      console.error(e)
    } finally {
      mutex.unlock();
    }
  }
}
```

However, JavaScript actually has a new keyword called using, balabala, and the transformed Mutex syntax can become like this:

```javascript
class Counter {
  private mutex = new Mutex();
  private value = 0;

  public async Inc() {
    using _ = mutex.lock();

    await sleep(Math.random() * 100);
    value++;
  }
}
```
