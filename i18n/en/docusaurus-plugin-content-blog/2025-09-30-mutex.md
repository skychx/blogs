## Initial Implementation

### Minimal Example

Let's first assume a simple concurrency scenario with a UserRegistry class for user registration, where you can call register to register a new user each time:

```typescript
const delay = (num: number) => new Promise((resolve) => setTimeout(resolve, num));

class UserRegistry {
  private users = new Set<string>();

  public async register(username: string): Promise<boolean> {
    if (this.users.has(username)) {
      return false;
    }

    await delay(Math.random() * 100); // Simulate other async operation costs
    this.users.add(username);

    return true;
  }
}
```

This register function implementation has read-write separation and uncertain async delays. If the outside world almost simultaneously registers a user named 'Bob', multiple users might register successfully, but actually only one user gets registered - a many-to-one situation:

```typescript
const center = new UserRegistry();

Promise.all([
  center.register('Bob'),
  center.register('Bob'),
  center.register('Bob'),
]).then((results) => {
  console.log(results); // Expected: [true, false, false], actual: [true, true, true]
});
```

This typical race condition problem stems from the fact that the check and insert operations in the `register` method are not atomic: there is an `await` between them, so all three calls finish their checks first (Bob doesn't exist yet at that point) and only then insert one after another. The check and insert operations **interleave** and trigger the BUG.

### Queued Processing

When encountering this kind of problem, a natural approach is queued processing. Each time register is executed, it doesn't directly execute the internal task, but pushes this task to a queue and then executes the code in this queue sequentially.

This transformation is also relatively simple. First create a queue, and each time register is called, wrap the real logic into a task and append it to the tail of the queue, so it runs only after all the previous tasks have finished. In JavaScript, such a queue can be represented by a single Promise chain:

```typescript
class UserRegistry {
  private users = new Set<string>();
  private queue: Promise<unknown> = Promise.resolve(); // The tail of the queue

  public register(username: string): Promise<boolean> {
    const task = this.queue.then(async () => {
      if (this.users.has(username)) {
        return false;
      }

      await delay(Math.random() * 100);
      this.users.add(username);

      return true;
    });

    // Whether the task succeeds or fails, the queue must keep moving
    this.queue = task.catch(() => {});

    return task;
  }
}
```

Run the test above again, and the result is consistently `[true, false, false]`.

However, this approach has obvious problems:

- The queuing logic is coupled with the business logic. Every method that needs mutual exclusion has to be wrapped like this, which is hard to reuse
- The whole method body runs inside the queue, so you can't lock just a small part of it. For example, parameter validation or network requests unrelated to Bob don't need to wait in line at all

So a better approach is to extract the "queuing" capability into a standalone mutex: call `acquire()` to take the lock and wait if it's not available; when you're done, call `release()` to hand the lock over to the next one.

## Using Promise.withResolvers

The key to implementing a Mutex is "waiting": when the lock is taken, `acquire()` must return a Promise that doesn't resolve for now, and the previous holder resolves it from the outside when it calls `release()`.

In the past, the only way to get the resolve function outside of a Promise was to write:

```typescript
let resolve!: () => void;
const promise = new Promise<void>((r) => {
  resolve = r;
});
```

This pattern is so common that many libraries wrap it in a Deferred class. Puppeteer has one too, and its source still contains the comment `// TODO: Switch to Promise.withResolvers with Node 22`.

`Promise.withResolvers()`, added in ES2024, does exactly this. It returns the promise together with its resolve and reject:

```typescript
const { promise, resolve, reject } = Promise.withResolvers<void>();
```

With it, the Mutex becomes very straightforward:

```typescript
class Mutex {
  #locked = false;
  #waiters: Array<() => void> = [];

  async acquire(): Promise<void> {
    if (!this.#locked) {
      this.#locked = true;
      return;
    }

    const { promise, resolve } = Promise.withResolvers<void>();
    this.#waiters.push(resolve);
    await promise;
  }

  release(): void {
    const next = this.#waiters.shift();
    if (!next) {
      this.#locked = false;
      return;
    }
    // Someone is waiting: keep the lock and hand it directly to the next one
    next();
  }
}
```

There are two details here:

- `#waiters` is a first-in-first-out queue. Whoever comes first gets the lock first, so nobody waits forever
- When someone is waiting, `release()` doesn't set `#locked` back to `false`. Instead it "hands over" the lock directly to the next waiter. If it set `false` first and then woke the waiter up, a newcomer could see the lock as free and take it before the woken waiter actually starts running, and two callers would end up in the critical section at the same time

Using it is the classic lock/unlock pattern. `release()` must be placed in `finally`, otherwise an exception thrown in the middle would leave the lock held forever:

```typescript
class UserRegistry {
  private users = new Set<string>();
  private mutex = new Mutex();

  public async register(username: string): Promise<boolean> {
    await this.mutex.acquire();
    try {
      if (this.users.has(username)) {
        return false;
      }

      await delay(Math.random() * 100);
      this.users.add(username);

      return true;
    } finally {
      this.mutex.release();
    }
  }
}
```

## Using `using`

At this point the Mutex already works, but try/finally is still a bit verbose, and it's easy to forget the release. Puppeteer uses another new syntax here: `using`.

`using` comes from the TC39 Explicit Resource Management proposal and has been supported since TypeScript 5.2. When a variable declared with `using` goes out of scope, whether the code finishes normally, returns early or throws, its `[Symbol.dispose]()` method is called automatically. It's a bit like Go's `defer` and Java's try-with-resources.

So all we need is to make `acquire()` return an object with a `[Symbol.dispose]()` method that releases the lock:

```typescript
class Mutex {
  #locked = false;
  #waiters: Array<() => void> = [];

  async acquire(): Promise<Disposable> {
    if (this.#locked) {
      const { promise, resolve } = Promise.withResolvers<void>();
      this.#waiters.push(resolve);
      await promise;
    } else {
      this.#locked = true;
    }

    return { [Symbol.dispose]: () => this.release() };
  }

  release(): void {
    const next = this.#waiters.shift();
    if (!next) {
      this.#locked = false;
      return;
    }
    next();
  }
}
```

The call site is now down to a single line:

```typescript
class UserRegistry {
  private users = new Set<string>();
  private mutex = new Mutex();

  public async register(username: string): Promise<boolean> {
    using _ = await this.mutex.acquire();

    if (this.users.has(username)) {
      return false;
    }

    await delay(Math.random() * 100);
    this.users.add(username);

    return true;
  }
}
```

The line `using _ = await this.mutex.acquire()` does two things: it first `await`s the lock, then uses `using` to bind releasing the lock to the current scope. No matter which branch returns, or whether an exception is thrown halfway, the lock is released when the function ends.

We use `using` rather than `await using` here because releasing the lock is synchronous, so implementing `Symbol.dispose` is enough. If cleaning up the resource is itself asynchronous (closing a file, disconnecting, etc.), you implement `Symbol.asyncDispose` and use it with `await using`.

Puppeteer's implementation ([Mutex.ts](https://github.com/puppeteer/puppeteer/blob/main/packages/puppeteer-core/src/util/Mutex.ts)) is basically the same as the one above:

```typescript
class MutexGuard {
  #mutex: Mutex;
  #onRelease?: () => void;
  constructor(mutex: Mutex, onRelease?: () => void) {
    this.#mutex = mutex;
    this.#onRelease = onRelease;
  }
  [disposeSymbol](): void {
    this.#onRelease?.();
    return this.#mutex.release();
  }
}

export class Mutex {
  static Guard = MutexGuard;

  #locked = false;
  #acquirers: Array<() => void> = [];

  // This is FIFO.
  async acquire(
    onRelease?: () => void,
  ): Promise<InstanceType<typeof Mutex.Guard>> {
    if (!this.#locked) {
      this.#locked = true;
      return new Mutex.Guard(this, onRelease);
    }
    const deferred = Deferred.create<void>();
    this.#acquirers.push(deferred.resolve.bind(deferred));
    await deferred.valueOrThrow();
    return new Mutex.Guard(this, onRelease);
  }

  release(): void {
    const resolve = this.#acquirers.shift();
    if (!resolve) {
      this.#locked = false;
      return;
    }
    resolve();
  }
}
```

There are two main differences:

- Waiting uses Puppeteer's own Deferred, the "predecessor" of `Promise.withResolvers` mentioned above
- `acquire()` returns a MutexGuard object and accepts an `onRelease` callback for some cleanup when the lock is released. For example, `BrowserContext` uses it to serialize screenshot operations while counting how many screenshots are still waiting

A typical use in Puppeteer is `ExecutionContext` registering bindings in the page. Several `waitFor*` calls may trigger a registration at the same time, so each one has to wait for the previous registration to finish before running:

```typescript
// If multiple waitFor are set up asynchronously, we need to wait for the
// first one to set up the binding in the page before running the others.
#mutex = new Mutex();
async #addBinding(binding: Binding): Promise<void> {
  if (this.#bindings.has(binding.name)) {
    return;
  }

  using _ = await this.#mutex.acquire();
  try {
    await this.#client.send('Runtime.addBinding', /* ... */);
    await this.evaluate(addPageBinding, 'internal', binding.name, CDP_BINDING_PREFIX);
    this.#bindings.set(binding.name, binding);
  } catch (error) {
    // ...
  }
}
```

### Compatibility

Both APIs are fairly new, so check your runtime before using them:

- `Promise.withResolvers`: ES2024, supported since Chrome 119, Firefox 121, Safari 17.4 and Node.js 22
- `using`: supported since Chrome 134, Firefox 141 and Node.js 24; Safari only has it in Technology Preview so far

In TypeScript, set `lib` to include `es2024` and `esnext.disposable` (or just use `esnext`). If the compile target doesn't support `using`, TypeScript turns it into try/finally, but the runtime still needs `Symbol.dispose`. You can add a polyfill first, just like Puppeteer does:

```typescript
(Symbol as any).dispose ??= Symbol('dispose');
(Symbol as any).asyncDispose ??= Symbol('asyncDispose');
```

## Comparison with Other Languages

Finally, let's compare with mutexes in other languages. Let's use the simplest example again. Suppose there's an Inc() function that operates on a variable, and we use random sleep to simulate the operation's time cost. In Go language, the similar pseudocode would be:

```go
type Counter struct {
    mutex sync.Mutex
    value int
}
func (c *Counter) Inc() {
    c.mutex.Lock()
    defer c.mutex.Unlock()

    time.Sleep(time.Duration(rand.Intn(100)) * time.Millisecond)
    c.value++
}
```

As you can see, in Go language, the main usage is to first instantiate a Mutex, then lock before Inc() execution, and unlock after Inc() execution completes.

Go syntax might be too sweet, so let's switch to another language, say Java, to see more calling details: lock at the beginning of Inc() execution, then unlock in the finally stage after the specific logic completes:

```java
public class Counter {
  private final ReentrantLock mutex = new ReentrantLock();
  private int value = 0;

  public void Inc() {
    mutex.lock();
    try {
      Thread.sleep(new Random().nextInt(100));
      value++;
    } catch (InterruptedException e) {
      e.printStackTrace();
    } finally {
      mutex.unlock();
    }
  }
}
```

The Java version corresponds to our try/finally version above. With `using`, the JavaScript version looks almost exactly like Go's `defer`:

```typescript
class Counter {
  private mutex = new Mutex();
  private value = 0;

  public async Inc() {
    using _ = await this.mutex.acquire();

    const value = this.value;
    await delay(Math.random() * 100);
    this.value = value + 1;
  }
}
```

Note, though, that locks in Go and Java are for multithreading: they prevent multiple threads from reading and writing the same memory at the same time. JavaScript is single-threaded, and a lone `this.value++` can't be interrupted. You only need a mutex when the read and the write are separated by an `await`, as in the example above.

## Summary

To sum up:

- Although JavaScript is single-threaded, a race condition can happen whenever an `await` sits between a read and a write
- `Promise.withResolvers` makes "resolving a Promise from the outside" simple, and with it you can easily build a first-in-first-out wait queue
- `using` calls `Symbol.dispose` automatically when leaving the scope, binding the lock release to the scope, so you never forget to release

Puppeteer's Mutex is only a few dozen lines, but it puts these new syntaxes to good use and is well worth learning from.
